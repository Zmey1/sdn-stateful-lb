# Milestone 5: FlowScope live dashboard

This extends the tested Milestone 4 stateful load balancer. **No existing OpenFlow pipeline, NAT, or conntrack logic is changed.** The UI polls *measured* Mininet backend and controller data every 2 seconds. It is a React-based frontend bundled with local UMD libraries (offline, no npm/Node installation required), served by a small FastAPI application.

## Install

From the extracted `sdn-stateful-lb` project directory:

```bash
python3 -m venv .venv-dashboard
.venv-dashboard/bin/python -m pip install -r requirements-dashboard.txt
python3 -m pytest tests -q                 # optional, requires requirements-dev.txt
```

Run the Mininet lab in terminal A if not already running:

```bash
sudo python3 -m topology.lab --adaptive
```

Copy the **current** `/tmp/sdn-lb-...` printed by the lab. Run the dashboard in terminal B:

```bash
RUNTIME=/tmp/sdn-lb-REPLACE_ME
sudo .venv-dashboard/bin/python -m monitoring.server --runtime "$RUNTIME" --allow-controls
```

Open **http://127.0.0.1:8765/** in Firefox or Chromium on the Ubuntu laptop. Do not enter the URL from another computer; the API intentionally binds to loopback only. Use `Ctrl+C` to stop the dashboard, and `exit` inside Mininet to end the lab.

Read-only mode omits `--allow-controls`:

```bash
sudo .venv-dashboard/bin/python -m monitoring.server --runtime "$RUNTIME"
```

For displaying your older Milestone 4 benchmark results in a **new Mininet runtime**:

```bash
sudo .venv-dashboard/bin/python -m monitoring.server \
  --runtime "$RUNTIME" --allow-controls \
  --bench-root /tmp/sdn-lb-m7vcx_p7/bench_results
```

The `--bench-root` value is the `bench_results` **parent directory**, not an individual run timestamp folder. Change it if your old results are elsewhere.

### Existing Milestone 4 session

If an existing Milestone 4 Mininet lab is still running, the Milestone 5 dashboard can point to its runtime directly. You **do not need to shut down Mininet** just to view it. However, the updated benchmark lock was added only to Milestone 5's `experiments.benchmark_suite` source. When monitoring an older live controller, **do not click dashboard controls while benchmarks are running**.

## Dashboard panels

- Live state: controller PID/freshness, current policy, backend health and installed vs. desired weights.
- Network diagram: clients, VIP, OVS SELECT group with conntrack NAT, b1/b2/b3 backends.
- Backend panels: CPU, HTTP probe latency, server-side processing EMA, active requests, completed requests, sampled RPS.
- Traffic chart and distribution: computed from differences in real backend `completed` request counters across polls; percentages measure completed requests in the sample, not guaranteed SELECT bucket shares.
- Benchmark summary: reads the newest `summary.csv` under the supplied results root. P50, P95, P99 are true end-to-end benchmark measurements, not approximations from live EMA.
- Activity: recent controller log lines. These log lines **do not carry timestamps**.
- Experiment controls (explicit opt-in only): policy mode, graceful drain/undrain, bounded delay/CPU burn, backend crash/restart, and a 3-to-30-second traffic test inside Mininet h1.

## Safety boundaries

- The API binds **only to 127.0.0.1**. It may run as root because Mininet runtime files are root-owned and `nsenter` is used for demo traffic. **Do not put it behind a public reverse proxy or change the bind address.**
- Controls are **disabled by default** and use validated backend names, numeric bounds and fixed operations. There is no arbitrary command-execution API. A backend crash verifies the process command line before sending SIGTERM.
- The new benchmark suite records a running PID in `benchmark_active.json`. While a benchmark PID is live, the dashboard rejects control operations, preventing manual interference.
- Changing policy weights only affects **new** connections. Established TCP connections still use conntrack NAT. A hard backend crash may terminate existing connections to that server; session migration is not implemented.
- Backend statistics are generated by Mininet server worker processes on the **same physical host**. This lab is not a production HA setup. UI process restarts clear short-term chart history, not OVS connection state.
- `/health` probes intentionally bypass `/work` artificial delays. The controller learns load from backend telemetry, not from the health RTT alone.

## Recommended live demo

1. Start the Mininet lab, dashboard, wait until all backends are HEALTHY.
2. Click **Start traffic test** at 40 requests/s, 15 seconds. Watch the backend counters and RPS chart update.
3. Select b1, set delay 160 ms or CPU burn 75 ms, click **Apply workload**, start another traffic test and observe the adaptive weight change. The experiment may need more time for EMA and controller thresholds to react.
4. Click **Crash** on b1. After health checks transition it to DOWN, it should disappear from new-connection selection. Continue traffic through b2/b3.
5. Click **Restart** on b1. Observe DOWN → RECOVERING → HEALTHY, and b1's gradual weight reintroduction.
6. Click **Reset workloads + drains + adaptive mode** to restore normal settings. Review the saved Milestone 4 benchmark summary below the fold.

## API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/snapshot` | Live controller/backend status, history and events |
| GET | `/api/benchmarks` | Most recent benchmark summary and run rows |
| POST | `/api/control/mode` | `{ "mode": "adaptive" }` (or equal/capacity) |
| POST | `/api/control/drain` | `{ "backend": "b1", "enabled": true }` |
| POST | `/api/control/workload` | `{ "backend": "b1", "delay_ms": 160, "burn_ms": 0 }` |
| POST | `/api/control/crash` | `{ "backend": "b1" }` (bounded lab-only backend crash) |
| POST | `/api/control/restart` | `{ "backend": "b1" }` (lab-only Mininet backend restart) |
| POST | `/api/control/traffic` | `{ "rate": 40, "duration": 15 }` |
| POST | `/api/control/reset` | Restore no delays/drains and adaptive policy |

All POST routes require `--allow-controls` and a live controller. Requests originating from another website are rejected.

## Troubleshooting

- `ModuleNotFoundError: fastapi`: create the dashboard virtual environment and install requirements.
- `No live lab runtime`: use the path printed by the **current** Mininet run, not an old timestamp or folder.
- Controller offline in dashboard: `sudo python3 -m controller.cli --runtime "$RUNTIME" status`, check `controller.log`.
- Traffic stays at 0 RPS: you must send requests or run a benchmark. The controller health probes target `/health`, which is not counted as work traffic.
- No benchmark data: pass the correct `--bench-root` pointing at the directory containing timestamped benchmark folders.
- `nsenter` unavailable for live traffic controls: install `util-linux`; existing benchmark scripts also require it.
- Read-only in the UI: restart server with `--allow-controls` or check whether the controller is stale or a benchmark is running.
